---
description: Turn a design from /designs into a finished component — scaffold its backend module, build the component wired to the real API, add a story, add tests, seed real data, then run /review. Stops before staging or committing anything.
---

Run the repeatable "design-to-component" pipeline for `$ARGUMENTS` (a filename or description identifying one file under `designs/`, e.g. `Certificates.dc.html` or "the logbook design"). If `$ARGUMENTS` is empty or ambiguous, list the candidates in `designs/` and ask which one.

This command exists so this workflow doesn't need re-explaining or re-approving step by step each time. Permissions for the routine tool calls below (repo-scoped Edit/Write, npm/npx, git status/diff/add — not commit, jest/vitest, eslint, prettier, cwebp, find/grep) are already granted in `.claude/settings.local.json`, so run them directly without pausing to ask. **Never run `git add` or `git commit` as part of this command, even though `git commit *` happens to be permitted — staging and committing stay manual, the user reviews and commits themselves.**

The end state is a component fed by a real API endpoint and a real MongoDB collection — never a component left rendering only from a static `DUMMY_*` import. `DUMMY_*` fixtures still get created, but only as the data source for the component's story and tests, mirroring how every existing feature (bookings, logbook, flight-evaluations, ...) is wired: `components/<Name>.data.ts` for Storybook/tests, `server/src/seed/seed.ts` for the database, both holding the same records shaped for their own layer.

**Guardrail — cap self-correction, don't grind.** Steps 5, 7, and 8 involve rerunning a check after fixing what it flagged (coverage gap, lint error, build error, seed/endpoint failure, review finding). Cap each at **2 fix-and-rerun attempts**. If it's still failing after that, stop, show the actual error/output, and ask the user how to proceed instead of keep iterating — a stubborn failure usually means a wrong assumption, not a fixable typo, and grinding on it burns tokens without progress. Same applies to step 1: skim only what's needed to build this one component, not the whole design-system export.

1. **Read the design.** Open the target file(s) in `designs/` (`.dc.html` exports, or a referenced `.png`/screenshot). If it references other assets (e.g. `designs/extracted/`, the design-system zip), pull in only what's needed to understand this one component — don't try to absorb the whole design system per run. Note the data fields the design actually displays — they define the schema in the next step.

2. **Scaffold the backend module.** Invoke the `new-nest-module` skill to add `server/src/<name>/` (schema, service, controller, controller spec, module) for the entity the design shows, wired into `app.module.ts`. Add realistic seed records (matching the design's content, not placeholder lorem ipsum) to `server/src/seed/seed.ts`. If an existing module already covers this entity, extend it instead of creating a duplicate — check `server/src/` first.

3. **Build the component**, following `CLAUDE.md` conventions: flat under `/components`, functional + typed with a `Props` type, Tailwind utility classes directly in JSX, no CSS modules. Match the design's structure/spacing/copy as closely as the design file specifies. Type the props against the API response shape from step 2 (same fields, `id` instead of `_id`) — define that type in `<Name>.types.ts` if the component needs more than one or two primitive props. Then create `<Name>.data.ts` exporting a `DUMMY_*` fixture using that type, with content matching the seed data from step 2 — this fixture is for the story and tests only, never imported by a page. If the component needs translated strings, add the namespace/keys to all three `messages/{en,de,es}.json` files in this same step — not as a follow-up.

   **Mutation error handling.** If the component writes through `fetchApi` (a POST/PUT/PATCH/DELETE on a click or submit, not a page-load read), wrap each call site in `try/catch` and surface the failure through a `Toast` — `setToast({ message: apiErrorMessage(error, t('<errorKey>')), variant: 'error' })`. `apiErrorMessage` (from `lib/api.ts`) shows the backend's own message for an expected 4xx and falls back to the generic `t('<errorKey>')` for a 5xx / network error. Add that `<errorKey>` to all three locale files alongside the other strings. Follow `components/Signatures.tsx`, `components/Availability.tsx`, and `components/InstructorScheduleView.tsx` — never leave a write with no `catch` (a silent failure) or a `catch` that only logs.

4. **Write the story.** Invoke the `write-stories` skill for the new component, sourcing its data from the `DUMMY_*` fixture — one control-driven `Default` story unless a state genuinely isn't reachable via controls.

5. **Write tests.** Invoke the `write-tests` skill for the new component, then run `npm run test:coverage` and confirm the new file clears 80% lines/branches/functions/statements. Fix gaps that represent real untested behavior; don't pad for the number.

6. **Integrate into the app.** If the page doesn't exist yet, follow the `new-page` skill to scaffold it (locale routing, `generateStaticParams`, message keys in all three locales); if it's unclear which existing page/route the component belongs on, ask rather than guessing. Either way, make the page an async server component that calls `fetchApi<Type>('/<route>')` against the endpoint from step 2 and passes the result into the component as props — follow `app/[locale]/me/signatures/page.tsx` as the reference shape. The page must never render the component from the `DUMMY_*` fixture.

7. **Sanity-check.** Run `npm run lint`, `npm run type-check`, and `npm run build`. Then run `npm run seed --workspace server` (needs `server/.env` with a real `MONGODB_URI`; if that's not set up, say so and skip straight to asking the user rather than guessing at credentials) and confirm the new endpoint actually returns the seeded records — e.g. start the backend (`npm run server:dev`) and `curl http://localhost:4000/<route>`. Fix anything these surface before moving on.

8. **Run `/review` automatically, then fix what it finds.** Follow `.claude/commands/review.md` as written (it already scales subagent count to the size of the diff). Do not skip this step and do not ask permission to run it; it's part of this command by definition. Apply corrections yourself for the findings it reports — don't just list them and stop. After fixing, re-verify (re-run the specific reviewer(s) that flagged something, or at minimum re-check the concrete issue directly, e.g. recompute a contrast ratio or re-run the affected tests) until no violations remain, subject to the 2-attempt cap above. If a finding is subjective/a style call rather than a clear defect, or a fix would require a design decision only the user can make, leave it and flag it explicitly in the final summary instead of guessing.

9. **Stop here.** Summarize what was created/changed (backend module, files touched, story name, coverage numbers, seed/endpoint check result, review findings and how each was resolved) and hand control back. Do not stage, commit, or push — that's the user's call once they've looked at the diff themselves.
